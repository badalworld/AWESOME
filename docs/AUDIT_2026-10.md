# Full pre-live audit — 2026-10-02

Scope: every path that can move money (`app/trade`, `app/risk`, `app/exchange/*`,
`app/engine.py`, `app/web`), plus the multi-venue isolation model and the account
configuration. Method: static analysis (`pyflakes`, `compileall`, targeted grep for
unsafe patterns), a line-by-line read of the order/exit state machine, adversarial
tests written for each suspected defect, and a live paper run of all three venues.

**Result: 18 defects found and fixed (11 on the money path or the dashboard), 151 tests
passing, replay of the live paper stack clean.** Details below, then the
live-readiness checklist and the honest $20 plan.

!!! note "Final market-only pass"
    Section **1b** covers the last pre-live instruction: *market orders only, no
    pending or limit orders anywhere*. It found five more defects (four of them
    capable of leaving a limit order on the book) and removed every remaining
    order-type knob.

---

## 1. Defects found and fixed

### C1 — `TypeError` inside the risk gate (Critical)

`RiskGuard.can_open()` built `GuardDecision(False, reason, {...})`, but
`GuardDecision` only has `(allowed, reason)`. The moment the **margin-utilisation
cap tripped** — i.e. exactly when the account is most exposed — the entry path
raised instead of returning a rejection.

*Fix:* real `detail` field on the dataclass. *Test:*
`test_audit_fixes.GuardDecisionTest`.

### C2 — Entry/exit fill confirmation was MEXC-only (Critical)

The executor confirmed fills through `client.order_by_id()` /
`order_by_external_id()` and parsed MEXC's `state` / `dealVol` / `dealAvgPrice`.
Binance and KuCoin have neither the methods nor those fields, so on those venues
the executor waited 2.5 s and then booked the **pre-trade hint price** — the
stop, the target, the ROI ladder and the booked P&L were all computed off the
wrong entry, and every live entry paid a 2.5 s stall. A second variant of the
same bug: `LiveBroker.set_callbacks()` wired the raw consumer straight into the
WebSocket, bypassing payload normalization entirely.

*Fix:* a normalized `order_status()` on all three venues
(`{"status","filled_qty","avg_price"}`), a `normalize_order_push()` on each
client, case-insensitive status handling, partial-fill awareness (a partial fill
is now risked and protected at its **real** size, not the requested one), and the
broker keeps the normalizing handler in the socket path.
*Tests:* `OrderStatusNormalizationTest`, `ExecutorFillPlumbingTest`,
`test_set_callbacks_keeps_the_normalizer_in_the_socket_path`.

### H1 — A resting target could survive a closed trade (High)

`LiveBroker.release_stop()` returned after cancelling the **first** leg. After a
watchdog/manual close on a venue without attached protection, the reduce-only TP
limit stayed on the book; a later position on the same symbol would have been
closed by that stale order. *Fix:* every leg (attached stop, standalone stop,
TPSL id, resting TP) is cancelled independently, none short-circuits the others.
*Test:* `test_release_stop_cancels_every_leg`.

### H2 — Protection was duplicated on every restart (High)

`Executor.restore()` unconditionally re-armed protection for each restored
position, placing a **new** exchange-side stop and TP on top of the ones already
resting from before the restart. Cumulatively: stacked stops, several reduce-only
TPs, and a book that no longer matched the bot's view. *Fix:* new
`open_protection(symbol)` per venue; the adopt path (`arm_protection(..., adopt=True)`)
queries the exchange first and *adopts* what is already there, placing orders only
when the venue answers "nothing rests" — and if the query itself fails it places
them anyway (unprotected is worse than duplicated) with a warning. *Tests:*
`test_adopt_existing_protection_instead_of_duplicating`,
`test_adopt_falls_back_to_placing_when_nothing_rests`.

### H3 — The venue minimum could 10x the intended risk (High — small account)

`size_position()` rounded **up** to `spec.min_vol` after computing the size and
never re-checked the budget. With $20 of equity (8 % ⇒ $1.60 margin ⇒ $16
notional), one contract of a symbol like `BTCUSDTM` is ~$100 notional: the bot
would have risked 6x the configured size, and the venue's own `MIN_NOTIONAL` was
ignored. *Fix:* venue-aware minimum (`spec.min_notional` **and** `min_notional_usd`),
a hard budget check after rounding, an availability check, and clear rejection
reasons that show up in the Signals tab; the universe scanner additionally drops
symbols whose smallest order can never fit the per-trade budget
(`universe.only_affordable_orders`, default on).
*Tests:* `SizingAffordabilityTest` (4 cases), plus the live engine run below.

### H4 — The dashboard's P&L and trade history were dead (High — dashboard)

Three separate wiring faults meant the numbers the dashboard showed were not the
numbers in the book:

* **Released P/L was always $0.00.** `db.trade_stats()` sums realised P&L into
  `total_pnl` while the analytics module calls the same figure `pnl`; the header
  read the second name from the first source. Now `state()` exposes
  `released_pnl` (closed trades), `open_pnl` (unrealised) and `total_pnl`, all
  from the right key, and `/api/venues` carries the same fields per venue so the
  three tabs agree with the header.
* **The trade history table was always empty.** `renderTrades()` read
  `payload.trades`, but no payload (WS frame or `/state`) contains a trades
  array — nothing ever fetched `/api/v/<venue>/trades`. The client now polls
  trades and the equity curve per active venue (and clears them on a tab switch,
  so venue A's history can never appear under venue B).
* **`starting_balance` did not exist.** The dashboard showed equity with no
  reference point, and the "starting" figure it did have silently followed the
  config. There is now a **fixed, persisted anchor** per venue
  (`account.starting_balance`): set on the first account snapshot of a book,
  untouched by restarts, deposits/withdrawals and config edits, and re-anchored
  only by an explicit paper reset. The header shows it next to equity, released
  P/L, win rate, open P/L and return %, all for the active tab's venue.

*Test:* `StartingBalanceAnchorTest` (3 tests) + `VenueIsolationTest`
(`released_pnl` is reported per venue, not summed across them).

### M1 — KuCoin exits had no fill price (Medium)

KuCoin answers a placement with only `orderId`. *Fix:* a bounded fill poll
immediately after **market** placements (never for resting orders, so protective
order latency is untouched), which also feeds the exit-booking path.
*Test:* `test_kucoin_dialect`, mapping tests.

### M2 — Live mode could be armed behind an open dashboard (Medium)

There was no link between "real orders" and "who can reach the control panel": a
token-less dashboard on `0.0.0.0` allows anyone who can reach the port to flatten
the account. *Fix:* live start is **refused** when `web.api_token` is empty *and*
the bind address is non-loopback, unless `web.allow_insecure_live = true`; the
dashboard shows a red banner whenever live is armed, and `/api/health` exposes the
posture. *Test:* `LiveSafetyGateTest` (3 cases).

### M3 — `/ws/{venue}` ignored the API token (Medium)

Every REST mutation checked the token, the state stream did not (it leaks equity,
positions and signals). *Fix:* the socket requires the token too; the dashboard
asks for it once on a 401, keeps it in `localStorage` and sends it on both REST
and WS.

### M4 — Wildcard CORS with credentials (Medium)

`allow_origins=["*"]` + `allow_credentials=True` is invalid per spec and lets any
web page talk to a control panel that places orders. *Fix:* CORS is **off** by
default (the dashboard is same-origin); set `web.allow_origins` to an explicit
list to enable it.

### M5 — A paper reset looked like a 98 % crash (Medium, found during the live run)

Resetting the paper book from $1000 to $20 left `RiskGuard.equity_peak` at $1000, so
the very next equity tick computed a 98 % drawdown and the **kill-switch halted all
three venues** — trading would have silently stopped until someone noticed. The same
thing would happen on a live account after a manual withdrawal/rebalance.
*Fix:* `RiskGuard.rebaseline(equity)` re-anchors the day/peak baselines and clears the
halt, and the paper-reset endpoint calls it. *Test:* `PaperResetRebaselineTest`.

### L1 — Identifiers interpolated into SQL (Low)

`db.py` interpolated dict keys into `INSERT`/`UPDATE` text (values were always
bound). Unguessable but avoidable. *Fix:* an identifier guard (`_safe_cols`)
raises on anything that is not a plain column name.

### L2 — Odds and ends (Low)

* `asyncio.get_event_loop()` in the venue summary (deprecated / creates loops in
  some contexts) → `time.time()` (verified fixed in `manager.summary()`; the
  audit's first pass claimed this without re-checking the file).
* Tick-coalescing sets were not cleared across an engine restart → cleared in
  `start()`.
* A position closed while the bot was offline was booked at $0 P&L with no marker
  → the trade now carries `pnl_unknown` + `closed_while_offline` in its metadata,
  so the dashboard/analytics can exclude it instead of silently averaging a
  fabricated zero.
* Engine tests asserted a hardcoded $1000 book, which would have masked the
  shipped $20 configuration → the harness now pins its own equity explicitly.

## 1b. Final market-only pass (2026-10-02, second sweep)

The last pre-live instruction was absolute: **market orders only — no pending or
limit orders anywhere** — with SL, TP and trail proven accurate on the live path.
A second sweep of the order path (entry → protection → trail → exit → repair)
found five more defects, four of which could put a *limit* order on the book:

| # | Severity | Defect | Fix |
|---|---|---|---|
| C3 | Critical | The +200 % ROI take-profit was placed as a **resting reduce-only LIMIT** (`LiveBroker.arm_protection`). A maker order that only fills at a price touch is exactly what the instruction forbids — and on a fast move it fills late or not at all while the bot believes the position is managed. | The target is enforced **locally**: `Executor.handle_tick` sends a reduce-only **market** close when the mark reaches it. `arm_protection` now places nothing but the stop. |
| C4 | Critical | MEXC `modify_plan_order` sent the new **trigger price as the `price` field** while `orderType=5`. If the venue reads `price` as an execution price, every trailing step silently converts the protective stop into a resting limit order — the classic "stop that does not fill" failure. | Market moves send `price: 0`; if a deployment refuses that, one retry sends the trigger price so the ratchet still happens (logged). Proven by `test_trailing_move_is_a_market_move_never_a_limit_price` and `test_trailing_move_falls_back_when_the_venue_refuses_price_zero`. |
| H5 | High | Cancelling a *legacy* attached take-profit on MEXC routed through `cancel_stop(kind="attached")`, which sends `stopLossPrice=0` — it would have cancelled the **stop** and left the position with no stop-loss and a live take-profit. | New `VenueClient.cancel_take_profit()`; MEXC implements the attached case as `change_stop_order(takeProfitPrice=0)` and leaves the stop-loss leg untouched (`test_attached_legacy_tp_is_cancelled_through_the_entry_order`). |
| H6 | High | A resting take-profit from an older build was **invisible** to MEXC's repair path: it is a regular (non-plan) reduce-only order, and `open_protection` never queried those. | `open_protection` also scans `GET /api/v1/private/order/list/open_orders` and reports reduce-only orders as legacy targets (entry orders are never touched), so adopt cancels them instead of adopting them (`test_legacy_reduce_only_limit_tp_is_cancelled_not_adopted`). |
| M6 | Medium | `_looks_like_attachment_error()` matched the bare token `"param"`, so a generic "invalid parameter" rejection would have triggered the fallback **entry** — a second order — and permanently disabled attached protection for that process. The `protection` label written after a fallback was wrong too. | Token list narrowed to genuine SL/TP rejection strings; ambiguous failures now fail safe (the entry is dropped, never doubled), and the label reflects what actually executed. |

Dead code and config conflicts removed in the same pass:

* `exchange.entry_order_type`, `exchange.exit_order_type` and
  `exchange.ioc_limit_buffer_bps` — validators, `config.toml` and the dashboard
  row — plus the `ioc_limit` branches in `LiveBroker.open_position`,
  `LiveBroker.close_position` and `MexcVenueClient.entry_order_with_protection`.
* `takeprofit.exchange_side` (dead key: read by nothing) and
  `takeprofit.close_remainder_on_tp` (only consumed by the deleted resting-TP
  path), including their dashboard/doc rows.
* `limit_order()` was deleted from all three venue clients **and** from the
  `VenueClient` interface, and `ORDER_IOC`/`ORDER_LIMIT` no longer exist: the
  codebase cannot place a limit order at all. `open_position()` lost its
  `tp_price` argument, so no call site can even ask for an exchange-side target.
* The paper broker now mirrors the live rule (it simulates only the stop), so
  paper and live exercise one identical code path — the +200 % ROI exit goes
  through the same market close on both.

What *does* rest on the exchange is the protective stop only:

* MEXC — attached SL on the entry order (`stopLossPrice` + `priceProtect=1`,
  no `takeProfitPrice`) or a standalone `planorder/place/v2` trigger with
  `orderType=5` and no execution price.
* Binance — `STOP_MARKET` with `closePosition=true`, `workingType=MARK_PRICE`.
* KuCoin — `type=market`, `stopPriceType=MP`, reduce-only.
* The local watchdog stays armed as a second line of defence if the stop order
  is ever rejected or lost.

Evidence: `tests/test_live_orders.py` (9 tests) drives the real
`MeXCClient → MexcVenueClient → LiveBroker` stack through a fake HTTP transport
that records every signed request body, and asserts field by field that entries,
stops, trailing moves and exits are all market orders and that no payload ever
carries a positive execution price — including one test that runs a whole trade
(entry → arm → three trail steps → exit) and checks the global invariant across
every request.

## 2. Audited and found correct (no change)

* **Signing**: MEXC `HMAC-SHA256(key + ts + body)`, Binance query-string HMAC,
  KuCoin `ts + METHOD + path?query + body` (+ base64 passphrase) — pinned by
  hand-computed vectors in `tests/test_venues.py`.
* **ROI math**: `ROI = move% × leverage` and its inverse, used for the ATR stop,
  the +200 % target and the whole trailing ladder; `stop_price_from_roi` (never
  `price_from_roi`) is used for stop placement.
* **Trailing**: activates at +30 % ROI, locks +20 %, `+10` stop per `+10` peak,
  ratchet-only, step-quantised, in *price* space (correct for both sides), never
  placed through the market, persisted every 5 s and on every step.
* **Risk guard**: max 10 positions, per-symbol cooldown, 80 % margin cap, daily
  loss halt, drawdown kill-switch, halt survives restarts.
* **Credentials**: AES-256-GCM with a 0600 machine key, per-venue rows in
  per-venue databases, never logged, never returned (masked preview only).
* **Isolation**: three engines, three SQLite files (WAL), three brokers/sockets;
  one venue failing to start never blocks the others; `VenueManager.summary()`
  reports each independently.
* **Position sync**: exchange-side fills, liquidations and manual closes are
  detected and booked; a close order that races a resting stop is recognised as
  "already flat" instead of double-counting.

## 3. Live-readiness checklist

Before flipping any venue to `live`:

1. **Set `web.api_token`** (e.g. `openssl rand -hex 24`) — otherwise live start is
   refused while the dashboard is on a public address, and if you override that,
   anyone on the port can trade.
2. **Per venue**: create a futures key with *order* permission, **IP-restrict it**,
   paste key/secret (+ KuCoin passphrase) in Settings → *Venue connection*, press
   *Save & verify*.
3. **Let it paper-trade first.** Watch the Signals tab for a few sessions: you
   want to see signals being *rejected* for concrete reasons (that is the filter
   stack working) and a handful of completed round trips.
4. **Start tiny.** Live on one venue first, smallest size, and check the first
   position end-to-end: entry fill price on the Positions card, the protective
   stop resting on the exchange (a trigger order that executes **at market**),
   one trailing step, and — when the mark reaches the target — the bot's own
   reduce-only **market** close. Nothing else should ever appear in the venue's
   open-orders list.
5. **Keep the halts on** (40 % drawdown, 25 % daily loss) and know where the
   *Flatten all* / *Pause* buttons are.
6. **Latency**: run on a VPS near the venue (Singapore/Tokyo/Frankfurt). The
   dashboard shows p50/p95/p99 per venue.
7. **Back up `data/`** — it holds the machine key and all three databases.
8. **Never run two instances** against the same API key/account.
9. Binance: the bot reads one-way vs hedge from the account and matches it.
   KuCoin: contracts sizing is per-symbol (`lotSize`), handled and tested.

Known limits (unchanged, documented honestly):

* Funding payments are not yet in the PnL.
* MEXC and KuCoin do not publish a per-contract min-notional over their APIs, so
  that side uses the shared `risk.min_notional_usd` ($5) plus each contract's
  minimum lot size; Binance's `MIN_NOTIONAL` filter *is* read per symbol.
* Liquidation price is not modelled (isolated margin + the 3×ATR stop is the
  protection).
* There is no exchange testnet switch, and this sandbox has no exchange
  connectivity — **the first live trade is the first real network test.**

## 4. The $20 plan (what changes on a small account)

Starting balance is now **$20** (`account.paper_starting_equity = 20.0`).

* At 8 % margin and 10x, one trade is **~$1.60 margin / ~$16 notional**. That
  clears MEXC's and Binance's ~$5 minimum notional, so MEXC/Binance are usable;
  symbols whose *smallest order* is larger than the budget are filtered out of the
  universe automatically (most KuCoin contracts, e.g. `BTCUSDTM` ≈ $100/lot).
* Ten concurrent positions at 8 % = 80 % of equity, exactly the configured
  margin cap — so `max_open_positions` is effectively self-limiting on $20.
* **$20 → $10,000 in 7 days is +143 %/day compounded (500x).** No setting makes
  that reachable: it needs ~42 consecutive full take-profits (+16 % equity each)
  with zero losses. Modelled probability: **< 1 %** — see
  [`docs/EDGE_AND_EXPECTANCY.md`](EDGE_AND_EXPECTANCY.md) (and, for the honest
  per-trade odds, [`docs/WIN_PROBABILITY.md`](WIN_PROBABILITY.md)), which now renders the
  whole report for a $20 start, including a growth ladder (what the same edge
  does over 7/30/90/365 days).
* Sensible small-account settings: keep the defaults (8 % / 10x / 10 positions),
  keep the halts, and let it compound — the same edge that turns $20 into $60 in
  a month needs a much bigger bankroll to reach $10,000, not more leverage.
* If the coin-flip variance at 8 %/trade is uncomfortable, the optional
  **partial take-profit** (`takeprofit.partial_tp_enabled = true`) banks half the
  position at +50 % ROI and lets the rest run: same edge, smaller swings, and it
  raises the effective break-even bar you have to clear
  ([`WIN_PROBABILITY.md`](WIN_PROBABILITY.md) §5, [`RISK.md`](RISK.md) §4).
